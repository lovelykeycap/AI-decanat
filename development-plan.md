# План разработки ИИ-аватара деканата

Статус: рабочий план после завершения продуктового аудита, реализация выполняется. Фактический прогресс и незакрытые проверки — [docs/progress.md](docs/progress.md), кандидат целевого комплекта — [docs/target-environment.md](docs/target-environment.md). Источник требований — [product-decisions.md](product-decisions.md), P-001–P-042. План ориентирован на полный согласованный продукт; промежуточные проверки компонентов не являются сокращённой поставкой.

## 1. Результат и границы

Поставка: устанавливаемое приложение для одного компьютера, русский голосовой диалог с контекстом, локальные ASR/TTS/аватар, ответы из подготовленной базы через Codex либо API, фотореалистичный персонаж в фиксированной сцене, перебивание, источники, защищённые настройки, обновление базы в даунтайме, журналы на 30 дней и инструкция киоск-развёртывания.

Не добавлять: оформление заявлений и справок, поиск по студентам, авторизацию студентов, другие языки, облачный аватар/голос, локальную LLM вместо согласованных провайдеров, поддержку двух производственных ОС, универсальный импорт документов, обновление базы посреди диалога, историю версий с ручным откатом, интеграцию с физическим терминалом. Возможность будущего источника данных обеспечивается небольшим интерфейсом поиска, а не системой плагинов заранее.

## 2. Техническое направление

Это решения для начала реализации, а не утверждение, что инструменты уже установлены и проверены. Точные версии фиксируются на этапе 0 после проверки совместимости. Если кандидат не проходит, обновить техническое решение с причиной; продуктовые требования самостоятельно не сокращать.

| Персонаж и сцена | Unreal Engine, MetaHuman, C++/Slate | Фотореалистичный готовый риг, движение тела обычными анимациями. UI и сцена в одном приложении без второго браузерного окна. Slate выбран при реализации, чтобы создать интерфейс кодом без отсутствующих widget-assets; продуктовые сценарии сохранены. |

| Оркестрация | Python, Pydantic, SQLite; отдельный локальный процесс | Общий для обеих веток поиск, контекст, валидация ответов, журнал и настройки. Отдельный процесс не связывает перезапуск генератора с рендером. |
| Речь → текст | whisper.cpp, мультиязычная Whisper-модель | Один движок для разработки на macOS и целевой Windows, разные аппаратные backends. Размер модели выбирать по русским записям и ресурсам. |

Сравнить с Piper только при проблемах качества или условий; финальный голос утверждает пользователь. |

| Codex | Изолированный адаптер `codex exec` с JSON Schema, входом владельца через ChatGPT | Штатный программный интерфейс вместо окон чата. Пригодность для данного сценария и аккаунта — обязательная ранняя проверка, не установленный факт. |

| Связь процессов | Локальный IPC: JSON-события + бинарный PCM, соединение с временным секретом | Сессия и реплика явно маркируются; команды не принимают shell-код. Не публиковать управляющий интерфейс в сеть. |

### Основание выбора и лицензии

- В [документации NVIDIA ACE 2.5](https://archive.docs.nvidia.com/ace/ace-unreal-plugin/2.5/ace-unreal-plugin-audio2face.html) локальное исполнение перечислено для Windows и NVIDIA. Наличие Linux у remote-provider не является подтверждением локального Unreal-provider на Linux. Архивная документация — отправная точка: в этапе 0 найти и закрепить поддерживаемую совместимую версию, не брать `latest` вслепую.
- [Unreal Engine](https://www.unrealengine.com/license) предусматривает бесплатное использование для образовательных учреждений; [MetaHuman](https://www.metahuman.com/license) включён в соответствующую лицензию UE. Это не разрешает произвольно распространять исходные ассеты; определить комплект поставки и права на каждый используемый материал.
- [whisper.cpp](https://github.com/ggml-org/whisper.cpp) поддерживает macOS и Windows, Apple Metal и NVIDIA. В macOS можно проверять реальную транскрипцию, не эмулируя Windows CUDA.
- Лицензии кода и весов проверяются раздельно. [Silero licensing](https://github.com/snakers4/silero-models/wiki/Licensing-and-Tiers) и актуальная карточка выбранной модели должны быть сохранены вместе с ревизией: нельзя считать все веса MIT по лицензии части репозитория. [Piper](https://github.com/OHF-Voice/piper1-gpl) имеет GPL-3.0; его встраивание и распространение рядом с UE требуют отдельной проверки совместимости. Не включать его в UE как библиотеку по умолчанию.
- [BGE-M3](https://huggingface.co/BAAI/bge-m3) — мультиязычный кандидат с MIT; качество поиска на нашем корпусе всё равно измеряется.
- Все ассеты и инструменты должны оставаться бесплатными для выбранного сценария. Если условия не подходят, искать бесплатную замену или документировать препятствие; платная покупка не является автоматическим решением.

### Почему сначала 3D

Нужно явно вставать и садиться, естественно переживать перебивание и слушать стоя. Управляемый риг позволяет разделить эти состояния и речь. Фиксированная камера используется для упрощения сцены, освещения и оптимизации. Не делать параллельно два полноценных аватарных продукта. MuseTalk/видеокласс рассматривать только если ранняя проверка 3D выявит конкретное непреодолённое ограничение; требования к движению, локальности и качеству при замене сохраняются.

## 3. Обязательные ранние проверки

### Codex как ветка продукта

[Неинтерактивный режим](https://learn.chatgpt.com/docs/non-interactive-mode) поддерживает `codex exec`, JSONL и схему финального ответа. [Аутентификация](https://learn.chatgpt.com/docs/auth) различает вход ChatGPT и API и содержит предостережение о публичных/недоверенных средах. Документация CLI сама по себе не подтверждает пригодность подписки для многопользовательского публичного помощника.

До закрепления интеграции:

1. Проверить официальный поддерживаемый способ и условия для сценария: посетители задают вопросы приложению, аккаунт и подписка принадлежат оператору. Зафиксировать, что подтверждено документацией/условиями, а что осталось неустановленным; при необходимости требуется разъяснение поставщика. Не объявлять изоляцию процесса доказательством разрешённости сценария.
2. Проверить на доступном аккаунте реальный короткий запрос, structured output, продолжение/отмену и ошибки лимитов без намеренного расходования лимита до нуля. Для ошибок использовать также контролируемые тестовые ответы.
3. Вызывать процесс без shell, с фиксированными аргументами и передачей вопроса через данные. Удалить доступ к проекту, секретам, произвольным MCP, web search и командам. Read-only sandbox сам по себе не означает запрета чтения всех файлов: проверить фактическую границу и доступные ограничения данной версии.
4. В агент передавать только текущую задачу ответа и найденные факты. Не предоставлять посетителям Codex UI, терминал или произвольное выполнение команд. Ссылки/инструкции внутри базы и речи не меняют системные правила.
5. Если требования изоляции или допустимость сценария не подтверждены, оставить этот пункт незакрытым. API-ветка позволяет продолжать независимую разработку, но не заменяет выполнением согласованную ветку подписки. Не использовать browser automation или извлечение токенов для обхода ограничения.

### Аватар в готовом приложении

Проверять **упакованное приложение**, а не только открытый Unreal Editor: совместимость UE/MetaHuman/ACE, локальность весов, работу Audio2Face на русском звуке, анимацию тела, отображение UI, генерацию и отмену PCM. Не рассчитывать на доступность editor-only API в релизе. Создание ассетов выполнять реальными инструментами редактора/скриптами и сохранять настоящие `.uasset`, не текстовые заглушки с такими именами.

### Оборудование

Рабочая гипотеза для стенда: NVIDIA RTX с 16 GiB VRAM, 32 GiB RAM, современный многоядерный CPU, SSD с запасом под модели/UE и качественный микрофон с динамиками. Это **не минимальные требования и не рекомендация к покупке до замеров**. Совместимость GPU определяется также поколением и драйвером, не только VRAM.

Определить фактический минимум по одновременной работе сцены, мимики, ASR, TTS и поиска. Сравнить CPU/GPU размещение речевых моделей, чтобы не отбирать память и вычисления у рендера. До этого не обещать работу на любой видеокарте. Требования редактора и компьютера для разработки отделить от требований готового приложения.

## 4. Архитектура поведения

### Сессия и состояния

Одна активная студенческая сессия на компьютер. Оркестратор — единственный владелец её состояния; Unreal отображает и подтверждает исполнение команд.

```text
ожидание (сидит)
  → начало разговора / вставание
  → слушает (стоит)
  → распознаёт / ищет / готовит ответ (стоит)
  → говорит (стоит)
  → слушает (стоит)
  → завершение / посадка
  → ожидание (сидит)
```

- По кнопке «Начать» вставать сразу, не ждать первого ответа. Речь во время вставания не терять.
- При заранее известной недоступности выбранной ветки без альтернативы не начинать диалог, оставаться сидеть и показать причину. Не гарантировать определение остатка лимита до запроса, если провайдер этого не предоставляет.
- Исчерпание лимита во время диалога: разрешённый fallback на API с тем же контекстом; иначе сообщение, завершение, посадка и очистка контекста.
- Перебивание: остановить именно слышимое аудио и очередь мимики, отменить текущую генерацию/синтез по возможности и принять новую реплику. Поздние результаты отменённой реплики игнорировать по `session_id/turn_id/generation_id`.
- Не считать неозвученную часть ответа уже услышанной: в контексте пометить прерванный ответ и фактически произнесённую часть. Текст и источники прерванной реплики могут оставаться в истории текущего диалога с явной пометкой.
- Не сохранять контекст в общую бесконечную Codex-сессию. Новый студент получает новую историю. Канонический контекст хранится приложением; provider-specific thread — деталь адаптера. Это позволяет fallback без потери реплик и исключает зависимость всей сессии от одного процесса Codex.
- Таймер: 60 секунд ожидания + предупреждение 15 секунд. Отсчёт не идёт во время распознавания, генерации, озвучивания и обработки новой реплики. Действия внутри «Источников» считаются активностью. Точное начало таймера после нажатия «Начать» — после окончания вставания, если студент ещё не заговорил.
- «Завершить» работает в любом состоянии: отмена задач, остановка звука, закрытие источников, очистка текста предыдущего студента, посадка. Устаревшие callback не оживляют завершённую сессию.

### Аудио и перебивание

Один компонент отвечает за захват и один — за воспроизведение. В AEC передаётся фактически воспроизводимый сигнал, а не только исходный WAV. После AEC/подавления шума работает VAD; сохраняется небольшой pre-roll в памяти, чтобы не терять начало слов. Конец реплики определяется локально, без подтверждения каждой фразы.

Одной команды отмены inference недостаточно: NVIDIA отмечает возможность краткого доигрывания буферизованных данных. Нужно отдельно останавливать playback, сбрасывать очередь кривых/PCM и завершать старую inference-сессию. Эти действия тестировать вместе на реальных динамиках, а не только на заранее записанном WAV.

Не определять уверенность ASR исключительно по тому, что строка непустая. При плохом сигнале, бессмысленном тексте либо неясном вопросе просить повторить/уточнить. Не заменять обязательное перебивание режимом с выключенным микрофоном во время ответа.

### Поиск и ответ

Общий для провайдеров конвейер: реплика + контекст → локальный hybrid retrieval → фрагменты с ID → генератор → проверка результата → TTS/экран/журнал.

Искать с учётом предыдущего предмета разговора, чтобы «А сколько её делают?» находило срок именно обсуждаемой справки. Сначала FTS5 и BGE-M3 dense с объединением результатов; reranker добавлять только при измеримом улучшении на контрольных вопросах. Поиск не обязан выбирать ответ, если данных нет.

Контракт `AnswerResult` для обеих веток:

```text
session_id, turn_id, kb_release_id
status: answer | clarify | insufficient_evidence | conflicting_evidence
answer_text: русский текст для экрана и озвучивания
source_ids: список ID переданных фрагментов
```

Системные ошибки провайдера передаются отдельно: `quota_exhausted`, `auth_required`, `network_unavailable`, `timeout`, `invalid_output`, `provider_error`, с признаком допустимости fallback. Невозможность ответить по базе не является поводом переходить на API или расходовать ещё один запрос автоматически.

Проверять схему, принадлежность цитат переданным фрагментам и наличие источников у фактического ответа. Сохранять важные даты и условия. Неподдержанные/некорректные результаты не озвучивать как факты. Schema и source ID не доказывают смысловую достоверность — её проверяют контрольные вопросы и сверка утверждений с evidence. Числовой `confidence` модели не считать гарантией.

### Сбои, настройки и хранение

Инженерное начальное значение общего тайм-аута генерации — 60 секунд, настраиваемое сотрудником. 10–20 секунд остаются согласованным нормальным ожиданием, а не обязательной задержкой. Без бесконечных повторов: не более одного контролируемого повторения при временной сетевой ошибке внутри общего тайм-аута; автоматически не повторять запрос после явного лимита/ошибки входа. Не переключать на API без включённой настройки.

При недоступности обеих веток завершить разговор с понятной причиной; при восстановлении разрешить новый. При отказе микрофона/голоса/аватара показать ошибку и не объявлять систему готовой к голосовому диалогу. Поведение уточняется реализацией и проверяется тестами, не вводит режим выдуманных офлайн-ответов.

Администратор: пароль с безопасным хешированием, настройки провайдера, выбор устройств, диагностика, база, журнал. Секреты — в защищённом хранилище ОС, не в пакете базы, репозитории или журнале. Вход в настройки не показывать как общедоступную кнопку на студенческом экране; конкретный жест/сочетание описать сотруднику, защитой является пароль, а не секретность жеста.

Журнал: SQLite, дата/время, ID сессии, вопрос, ответ, статус, провайдер, версия базы и снимки источников. Очистка старше 30 дней при запуске и по расписанию; диагностические логи не дублируют бессрочно тексты. Аудио — только в ограниченных буферах памяти; временные файлы TTS, если без них нельзя, удаляются после использования и при следующем запуске после сбоя. Промежуточный PCM не является архивом исходного микрофона.

Киоск: полноэкранность в приложении и отдельная конфигурация ограниченной учётной записи Windows. Обычный fullscreen не считается защитой от системных сочетаний. Проверить редакцию Windows и доступные средства блокировки; не обещать запрет всех системных действий только флагом UE. Сотрудник сохраняет документированный способ обслуживания.

## 5. Этапы реализации и условия завершения

Выполнять по порядку зависимостей. Независимые задачи можно чередовать; при отсутствии GPU не останавливать работы, проверяемые на MacBook. Каждый этап закрывается артефактом и результатом проверки, а не сообщением «готово».

### Этап 0. Проверить техническую осуществимость

- Зафиксировать характеристики доступного MacBook и доступные среды, проверить репозиторий и инструкции.
- Проверить Codex-интеграцию и ограничения по разделу 3, подобрать API-модель без выдуманного имени и проверить разрешённый доступ, когда аккаунт доступен.
- Составить совместимую матрицу UE/MetaHuman/ACE/драйверов/Python/моделей. Проверить лицензии, бесплатность и порядок получения ассетов и весов.
- Создать минимальный технический стенд мимики на русском PCM и движения тела. На Mac выполнить только поддерживаемые операции; CUDA/package проверку отметить ожидающей целевого стенда.
- Зафиксировать выбор ОС и кандидата аппаратной конфигурации в `docs/technical-decisions.md`. Если требуется сменить связку, принять решение здесь до массовой разработки сцены.

Выход: воспроизводимые инструкции, список зависимостей/лицензий, реальные результаты и явно отмеченные непроверенные пункты. Без GPU-проверки нельзя объявить этот этап полностью пройденным, но следующие независимые этапы можно выполнять.

### Этап 1. Контракты и каркас

- Создать `backend/`, `desktop/`, `native/audio/`, `schemas/`, `tests/`, `tools/`, `docs/`, `assets/manifest/`.
- Реализовать типизированные команды/события и `AnswerResult`, идентификаторы сессий/реплик, конфигурацию и единый state machine.
- Закрепить версии/контрольные суммы зависимостей. Большие модели и ассеты получать по воспроизводимому манифесту, не складывать бинарные веса в обычную историю Git.

Проверка: переходы состояний, отмена, запоздалые события и сброс сессии выполняются без реальных внешних провайдеров. Тестовые адаптеры используются только для проверки, не выдаются за финальные компоненты.

### Этап 2. База знаний и поиск

- По контракту создать JSON Schema, пакет с явно вымышленными примерами и понятные ошибки валидатора.
- Реализовать импорт в режиме обслуживания, построение FTS5/dense-индекса и безопасную замену базы без истории версий.
- Реализовать provenance, отображение источников и снимки цитат для журнала.
- Подготовить контрольный корпус: обычные вопросы, перефразировки, точные номера/названия, последующие уточнения, отсутствие фактов, противоречия и инструкции внутри данных.

Проверка: повреждённый пакет не меняет базу; обновление запрещено во время разговора; найденные источники воспроизводимы; отсутствие совпадения не превращается в утверждение.

### Этап 3. Две ветки ответа

- Реализовать API-адаптер и Codex-адаптер с общей канонической историей, evidence и schema.
- Добавить валидацию источников, статусы отсутствия сведений/уточнения/противоречия, нормализацию ошибок.
- Реализовать ручной выбор режима и fallback только при включённой настройке, сохранение контекста при переключении, лимит общего времени и остановку отменённых запросов.
- Для Codex проверить отсутствие лишнего доступа и сохранения нежелательных rollout. Ephemeral-режим, если доступен, не приравнивать к отсутствию хранения данных у поставщика.

Проверка: оба провайдера реально отвечают на одном контрольном наборе; тесты ошибок/лимитов не требуют исчерпывать подписку. Если аккаунт/разрешённость интеграции не подтверждены, соответствующая проверка остаётся незакрытой.

### Этап 4. Речь и полный дуплекс

- Реализовать выбор микрофона/динамиков, AEC/NS, VAD, pre-roll и endpointing.
- Подобрать Whisper-модель на русской речи с названиями кафедр, фамилиями, аббревиатурами и номерами аудиторий.
- Подобрать бесплатный допустимый TTS-checkpoint; нормализовать числа, даты и сокращения без изменения фактов. Подготовить образец голоса.
- Проверить реальное перебивание с динамиками, отмену и остановку очереди; исходный микрофон не сохранять на диск.

Проверка: собственная речь не запускает вопросы, первые слова не обрезаются, неясные вопросы уточняются, перебивание не теряет новую реплику. Нужен реальный акустический тест, не только программная симуляция.

### Этап 5. Персонаж и сцена

- Самостоятельно выбрать образ: вымышленный сотрудник с нейтральной деловой внешностью, голос подбирать в соответствии с ним; представить пользователю образец, не считать его заранее утверждённым.
- Создать бесплатные сцену, ноутбук/стол/стул и материалы; для простых предметов допустимы собственные модели. Для чужих ассетов сохранять происхождение и лицензию.
- Создать/ретаргетировать анимации сидения, вставания, слушания, речи, посадки. Проверить руки, контакт со стулом/столом, отсутствие скольжения и пересечений.
- Подключить локальную мимику, моргание и сдержанные idle-движения. Синхронизировать мимику со слышимым PCM, сбрасывать их вместе при перебивании.
- Настроить постоянный ракурс, свет, LOD и волосы под ресурсный бюджет.

Проверка: согласованный цикл виден целиком, переходы естественны, русская речь синхронна; runtime работает без облачного аватарного сервиса и без открытого редактора. Ассеты и голос утверждены пользователем.

### Этап 6. Полный студенческий и служебный интерфейс

- Slate-экран: аватар, «Начать», «Завершить», «Источники», вопрос/ответ, состояния ожидания и ошибок, предупреждение тайм-аута.
- Настройки по паролю: провайдер и разрешение API-fallback (по умолчанию выключено), устройства, диагностика, обновление базы в даунтайме и просмотр журнала.
- Очистка всех следов предыдущей сессии на студенческом экране, таймер 60+15, закрытие источников при завершении.
- Начальная настройка при отсутствии базы/моделей/аккаунта: понятная диагностика для сотрудника вместо сломанной кнопки разговора.

Проверка: студент не попадает в админ-функции, ошибки не показывают секреты/трассировки, действия с источниками не открывают рабочий стол, сессия завершается из любого состояния.

### Этап 7. Сборка, развёртывание и восстановление

- Собрать packaged Windows-приложение и backend, включить нужные runtime-зависимости. На чистом компьютере не требовать установки средств разработки.
- Создать установку/проверку моделей с контрольными суммами и понятной ошибкой недостающих лицензируемых компонентов. Зафиксировать допустимые правила их распространения.
- Настроить запуск и завершение дочерних процессов, восстановление после падения, старт в безопасном состоянии с пустой студенческой сессией.
- Подготовить киоск-профиль выбранной редакции Windows, инструкцию входа сотрудника и обслуживания. Проверить полный запуск после перезагрузки.

Проверка: установка на чистой целевой ОС, запуск без UE Editor, отсутствие общедоступных секретов, корректное восстановление после остановки backend и прерывания обновления базы.

### Этап 8. Сквозная приёмка и оптимизация

- Выполнить матрицу ниже на полном продукте, отдельно для Codex и API, используя один набор данных.
- На GPU-стенде измерить память, кадры, фактическую задержку и перебивание при одновременной работе всех локальных компонентов.
- Настроить качественный режим по результатам, затем опубликовать измеренные минимальные требования в `docs/system-requirements.md`.
- На реальной утверждённой вузом базе проверить факты. Синтетический корпус проверяет механику, но не заменяет эту приёмку.
- Подготовить инструкции сотруднику, лицензионный перечень, отчёт о проверках и список известных ограничений.

Готовность: все обязательные сценарии проходят в целевой среде, нет подмены реальных ASR/TTS/аватара/провайдеров заглушками, нет незакрытой зависимости на готовность ассетов, аккаунта или реальной базы. Не объявлять продукт принятым по одним backend-тестам на MacBook.

## 6. Матрица приёмки

Числовые показатели ниже — начальные инженерные критерии, а не дополнительные требования преподавателя. При первом измерении уточнить условия стенда и объём выборки, не менять продуктовые правила ради зелёного отчёта.

| Проверка | Ожидаемый результат | Где |
| --- | --- | --- |
| Факты и источники | На контрольном наборе все существенные утверждения подтверждены; неизвестные ID отклонены. Отдельно проверяются даты, сроки, документы и контакты. | macOS/backend + реальная база при приёмке |
| Нехватка данных/конфликт | Нет выдуманного ответа, есть согласованное уточнение/сообщение; найденный конфликт не разрешается моделью самовольно. | Обе реальные ветки + сценарные тесты |
| Контекст | «А сколько её делают?» относится к предыдущей услуге; следующему студенту история не передаётся. | Backend + целевое приложение |
| Лимит и fallback | Выключен по умолчанию; известный лимит оставляет аватара сидеть; ошибка в диалоге без альтернативы завершает его и усаживает. | Сценарные тесты + целевая сцена |
| Перебивание | Цель — прекращение слышимой речи до 500 мс после подтверждённого начала речи студента; новая реплика не теряется, поздний ответ не воспроизводится. | Реальные динамики/микрофон на целевом ПК |
| Эхо | На 30 контрольных ответах без речи студента собственная озвучка не создаёт новых реплик; отдельно 30 попыток перебивания в разных местах фразы. | Реальная акустика; результат не обобщается на любое помещение |
| Бездействие | 60 секунд + 15 секунд предупреждения, исключены генерация и речь; завершение очищает студенческий экран/контекст. | Управляемые часы в тестах + UI |
| Задержка | Записать p50/p95 и холодный старт минимум на 50 репликах каждой реальной ветки. Основной рабочий диапазон — согласованные 10–20 с; превышения разобраны, а не скрыты заглушкой. | Целевой стенд + сеть/реальные аккаунты |
| Изображение | Цель — устойчивые 30 FPS при согласованном качестве на 1080p; образец утверждён, движения и lip-sync проверены визуально. | Полная целевая сборка |
| Обновление | Во время разговора недоступно; неверный пакет не меняет базу; после сбоя нет смеси индексов/фактов. | Backend + целевой ПК |
| Хранение | Журнал доступен сотруднику, записи старше 30 дней удаляются; аудио микрофона и секреты не попадают в файлы приложения. | Файловая проверка + тесты времени |
| Надёжность | Восьмичасовой прогон с серией диалогов и отмен, без нарастающих утечек памяти/процессов; сбой провайдера не оставляет зависшую сессию. | Целевой ПК |
| Киоск | Ограниченная учётная запись не даёт студенту выйти в рабочий стол стандартными предусмотренными сценариями; сотрудник имеет рабочий способ обслуживания. | Выбранная редакция Windows |

ASR оценивать по ошибкам важных сущностей и WER на размеченной русской выборке, TTS — по произношению фамилий/номеров/сроков и прослушиванию. Не назначать произвольный порог cosine similarity или уверенности модели гарантией качества. Контрольные записи для разработки хранить только как специально подготовленные тестовые материалы, не как скрытые записи студентов.

## 7. Проверки на MacBook и внешние зависимости

| Можно делать сейчас на macOS | Требуется целевая Windows/NVIDIA либо внешний материал |
| --- | --- |
| Контракты, state machine, база, retrieval, журнал, настройки backend | Проверка локального ACE-provider и общего GPU-бюджета |
| Реальный Whisper и подходящий локальный TTS, аудиологика на доступных устройствах | Windows audio/драйверы, реальное эхо и перебивание на предполагаемых устройствах |
| Codex/API по доступности аккаунтов; ошибки через контролируемые адаптеры | Право и доступ к рабочему аккаунту оператора; реальные обе ветки при приёмке |
| Сцена и ассеты в доступных macOS-инструментах, если хватает ресурсов | Packaged-build, чистая установка, киоск-политики и длительный прогон |
| Синтетический явно маркированный корпус | Реальная подготовленная и утверждённая база вуза |

Платный GPU-сервер, покупка компьютера или новые платные сервисы не заказываются автоматически. Доступ к стенду организуется отдельно, когда будет понятна конфигурация. До него продолжаются независимые этапы, а неподтверждённые проверки остаются честно открытыми.

## 8. Порядок ведения работы

Вести `docs/progress.md`: этап, сделанные артефакты, выполненные проверки, измерения и конкретные оставшиеся зависимости. Обновлять после значимых изменений. Матрицу P-ID → компонент → проверка добавить при реализации, чтобы ни одно согласованное требование не потерялось.

Сначала выполнить этап 0 и каркас контрактов, затем базу/провайдеры и речь; сцену разрабатывать после ранней проверки её стека. Утверждение реального образца — единственная запланированная визуальная точка согласования; не возвращаться к опросу про уже принятые решения. Обычные технические детали выбирать самостоятельно, со ссылкой на требования и измерения.
